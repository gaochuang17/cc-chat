# 流式聊天接口

> 本文档详细介绍 /api/chat 接口的完整实现，包括 SSE 流式响应、数据库交互、以及 LLM 调用的流程。

---

## 一、SSE（Server-Sent Events）简介

SSE 是一种 HTTP 流式传输协议，服务器可以持续向客户端推送数据，直到连接关闭。

### SSE vs WebSocket

| 特性 | SSE（本项目） | WebSocket |
|------|-------------|-----------|
| 方向 | 服务器 -> 客户端（单向） | 双向 |
| 协议 | HTTP | 独立协议（ws://） |
| 重连 | 浏览器自动重连 | 需手动实现 |
| 复杂度 | 低 | 高 |
| 适用 | 流式输出（LLM 回复） | 实时聊天室、游戏 |

对于 AI 聊天，只需要服务器向客户端推流，SSE 足够且更简单。

### SSE 数据格式

SSE 的每条消息以 `data: ` 开头，以两个换行 `\n\n` 结尾：
``
data: {"content": "你好"}\n\n
data: {"content": "！"}\n\n
data: [DONE]\n\n
``

本项目定义了三种消息类型：
* `{"content": "片段"}`：AI 回复的文本片段
* `{"error": "错误信息"}`：LLM 调用出错
* `[DONE]`：回复结束标记

## 二、接口实现全流程

`api/chat.py` 的 `/api/chat` 接口是整个项目最复杂的部分：

```python
@router.post("/chat")
async def chat(
    req: ChatRequest,
    user: User = Depends(current_active_user),
    db: AsyncSession = Depends(get_async_session),
):
    # 1. 验证对话归属
    conv = await _verify_conversation(req.conversation_id, user, db)

    # 2. 保存用户消息
    user_msg = Message(conversation_id=conv.id, role="user", content=req.message)
    db.add(user_msg)

    # 3. 首条消息自动更新标题
    if conv.title == "新对话":
        conv.title = req.message[:50]
    await db.commit()

    # 4. 从数据库加载完整历史
    result = await db.execute(
        select(Message)
        .where(Message.conversation_id == conv.id)
        .order_by(Message.created_at)
    )
    history = result.scalars().all()

    # 5. 组装 LLM 上下文
    llm_messages = [{"role": "system", "content": settings.SYSTEM_PROMPT}]
    for msg in history:
        llm_messages.append({"role": msg.role, "content": msg.content})

    # 6. 流式返回
    return StreamingResponse(
        stream_and_save(llm_messages, conv.id),
        media_type="text/event-stream; charset=utf-8",
    )
```

### 步骤详解

**步骤 1：验证对话归属**
```python
async def _verify_conversation(conversation_id, user, db):
    conv = await db.scalar(
        select(Conversation).where(
            Conversation.id == conversation_id,
            Conversation.user_id == user.id,
        )
    )
    if conv is None:
        raise HTTPException(status_code=404, detail="对话不存在")
    return conv
```
检查对话是否属于当前用户，防止越权。

**步骤 2-3：保存用户消息 + 自动标题**
用户消息先存入数据库，然后从数据库重新加载（步骤 4），确保发给 LLM 的历史包含刚保存的消息。

**步骤 3 的标题逻辑：** 如果对话标题还是默认的 "新对话"，说明这是第一条消息，用消息前 50 个字作为标题。这是 ChatGPT 的行为模式。

**步骤 4：加载历史**
从数据库按时间顺序加载该对话的所有消息（包括刚保存的用户消息）。

**步骤 5：组装上下文**
OpenAI API 要求 `messages` 参数是 `[{role, content}, ...]` 格式。我们在最前面插入 `system` 提示词：
```python
[
    {"role": "system", "content": "你是一个有用的AI助手..."},
    {"role": "user", "content": "第一句话"},
    {"role": "assistant", "content": "回复一"},
    {"role": "user", "content": "第二句话"},
    ...
]
```

**步骤 6：返回 StreamingResponse**
`StreamingResponse` 接收一个异步生成器，将其产出逐个发送给客户端。`media_type="text/event-stream"` 告诉浏览器这是 SSE。

## 三、流式生成器 stream_and_save

这是整个后端最关键的函数：

```python
async def stream_and_save(llm_messages, conversation_id):
    accumulated = ""  # 累积完整 AI 回复

    try:
        # 逐 token 从 LLM 获取，通过 SSE 发给前端
        async for chunk in stream_chat_raw(llm_messages):
            accumulated += chunk
            data = json.dumps({"content": chunk}, ensure_ascii=False)
            yield f"data: {data}\n\n"

        # 流结束后，把完整回复写入数据库
        async with async_session_maker() as session:
            msg = Message(
                conversation_id=conversation_id,
                role="assistant",
                content=accumulated,
            )
            session.add(msg)
            await session.commit()

        yield "data: [DONE]\n\n"  # 通知前端回复结束

    except Exception as e:
        error_data = json.dumps({"error": str(e)}, ensure_ascii=False)
        yield f"data: {error_data}\n\n"
```

### 为什么用独立 Session

```python
# 不用注入的 db，而是自建 session
async with async_session_maker() as session:
    ...
```

**核心问题：** `StreamingResponse` 的生成器在路由函数返回后才开始执行（流式发送）。此时 FastAPI 已经清理了 `Depends(get_async_session)` 注入的 Session。如果在已关闭的 Session 上 commit，会报错。

**解决方案：** `stream_and_save` 内部用 `async_session_maker()` 创建独立的 Session，与请求生命周期解耦。

### 为什么先流式后存储

``+LLM 生成中:  token1 → token2 → token3 → ... → tokenN
              ↓        ↓        ↓                ↓
SSE 发送:     yield    yield    yield           yield

生成完成后:
              accumulated = token1 + token2 + ... + tokenN
              → 存入数据库
```

用户消息在发送请求时就存了，AI 回复在全部生成完后才存。这样做的原因：
* 流式过程中可能出错（网络断开、LLM 异常），此时 accumulated 不完整
* 只有流成功完成后才存储完整的 AI 回复
* 如果出错，走 except 分支发错误给前端，不存数据库

### `ensure_ascii=False`

```python
json.dumps({"content": chunk}, ensure_ascii=False)
```
`ensure_ascii=False` 让 JSON 中保留中文字符，而不是转义成 `\uXXXX`。这样 SSE 数据更短，也更容易调试。

### `yield` 的本质

`yield` 让 `stream_and_save` 成为一个异步生成器。每次 `yield` 时，数据被发送给客户端，然后函数暂停，等待下一次被请求时继续执行。

```
后端:  yield "data: {content: 你}\n\n"  → 发给前端 → 暂停
       yield "data: {content: 好}\n\n"  → 发给前端 → 暂停
       ... 直到 [DONE]
```

## 四、LLM 调用 core/llm.py

```python
async def stream_chat_raw(messages: list[dict]):
    client = get_client()
    response = await client.chat.completions.create(
        model=settings.OPENAI_MODEL,
        messages=messages,
        stream=True,  # 关键：开启流式
    )
    async for chunk in response:
        if not chunk.choices:
            continue
        delta = chunk.choices[0].delta
        if delta.content:
            yield delta.content  # 只返回文本片段
```

### 流式响应的数据结构

非流式模式返回完整回复：
```python
response.choices[0].message.content  # "你好！有什么可以帮你的？"
```

流式模式逐 token 返回：
```python
# chunk 1: choices[0].delta.content = "你"
# chunk 2: choices[0].delta.content = "好"
# chunk 3: choices[0].delta.content = "！"
# ...
# 最后一个 chunk: choices[0].finish_reason = "stop", delta.content = None
```

`delta` 是增量：每次只返回新增的部分，不是完整内容。

### 兼容多种 LLM 提供商

通过 `OPENAI_BASE_URL` 切换提供商：
* OpenAI：`https://api.openai.com/v1` + `gpt-4o-mini`
* DeepSeek：`https://api.deepseek.com` + `deepseek-chat`
* 通义千问：`https://dashscope.aliyuncs.com/compatible-mode/v1` + `qwen-plus`
* 本地 Ollama：`http://localhost:11434/v1` + `qwen2.5:7b`

所有提供商都兼容 OpenAI API 格式，只需改配置不需要改代码。

## 五、错误处理

```python
try:
    async for chunk in stream_chat_raw(llm_messages):
        ...
except Exception as e:
    error_data = json.dumps({"error": str(e)}, ensure_ascii=False)
    yield f"data: {error_data}\n\n"
```

常见错误：
* API key 无效或未配置
* 网络连接失败
* 模型名称错误
* Token 超限（对话太长）
* LLM 服务不可用

错误通过 SSE 的 `{"error": "..."}` 消息发给前端，前端在 AI 气泡中显示错误信息。

**注意：** 出错时不发 `[DONE]`，前端通过 JSON 中的 `error` 字段识别错误。如果发了 `[DONE]` 前端会误认为回复正常结束。

## 六、完整时序图

```
前端              后端路由            LLM             数据库
  │                 │                  │                 │
  │  POST /chat     │                  │                 │
  ├────────────────→│                  │                 │
  │                 │  验证对话归属     │                 │
  │                 ├──────────────────→│                 │
  │                 │  保存用户消息     │                 │
  │                 ├────────────────────────────────────→│
  │                 │  加载历史         │                 │
  │                 ├────────────────────────────────────→│
  │                 │  组装上下文       │                 │
  │                 │  调用 LLM(stream) │                 │
  │                 ├─────────────────→│                 │
  │                 │                  │                 │
  │  SSE: token1    │  yield "你好"    │                 │
  │←────────────────┤←─────────────────│                 │
  │  SSE: token2    │  yield "！"      │                 │
  │←────────────────┤←─────────────────│                 │
  │  ...            │  ...             │                 │
  │  SSE: [DONE]    │                  │                 │
  │                 │  保存AI回复       │                 │
  │                 ├────────────────────────────────────→│
  │←────────────────┤                  │                 │
  │  连接关闭        │                  │                 │
```

SSE 的关键在于：后端在 LLM 生成的同时就把数据推给前端，不需要等全部生成完才返回。这就是"打字机效果"的实现原理。
