# CC-Chat 开发文档总览

> AI 聊天助手（ChatGPT 风格）前后端分离项目的完整开发记录。
> 开发日期：2026-08-14

---

## 一、项目定位

构建一个类似 ChatGPT 的 AI 聊天助手，具备以下核心功能：

- 用户注册 / 登录（JWT 认证）
- 多会话管理（创建、切换、删除对话）
- 流式聊天（打字机效果，逐字输出）
- 历史消息持久化（切换对话时自动恢复）
- Markdown 渲染 + 代码高亮

## 三、为什么这样选型

### 3.1 后端为什么选 Python + FastAPI

**用户最初的问题：** 后端用 Python 有什么好处？能用其他技术栈吗？

Python 的优势：
- **生态丰富**：AI / LLM 领域的库几乎全部有 Python 版本（OpenAI SDK、LangChain 等），天然适合 AI 应用
- **开发效率高**：语法简洁，适合快速原型开发
- **学习曲线平缓**：对后端零基础的人更友好

其他可选方案：
- **Node.js (Express/NestJS)**：前后端统一语言（TypeScript），但对 AI 生态不如 Python
- **Go (Gin)**：性能极佳，但学习成本高，AI 库少
- **Java (Spring Boot)**：企业级首选，但对小项目过重

结论：鉴于项目核心是 AI 聊天，Python 是最优选择。

### 3.2 数据库为什么选 SQLite

- 零配置：不需要安装数据库服务器，一个文件就是整个数据库
- 学习友好：SQL 语法和真实数据库（MySQL/PostgreSQL）一致，迁移成本低
- 够用：单机小项目完全够用，后续可无缝迁移到 PostgreSQL

### 3.3 认证为什么选 fastapi-users

- 封装了注册、登录、JWT 生成/校验、密码哈希等全部逻辑
- 开箱即用的路由（register / login / logout / users/me）
- 官方支持 SQLAlchemy 异步集成
- 不用自己手写密码哈希、JWT 签名等安全敏感逻辑

### 3.4 前端为什么选 React + Ant Design

- React：生态最成熟、社区最大的前端框架
- Ant Design：企业级组件库，表单、菜单、按钮等组件开箱即用
- TypeScript：配合 Vite 提供类型安全和极速热更新

## 五、数据流详解

### 5.1 认证流程

```
注册:  前端 → POST /api/auth/register {email, password}
       → 后端创建用户（密码哈希存储）→ 返回用户信息
       → 前端自动调用登录

登录:  前端 → POST /api/auth/jwt/login (表单格式)
       → 后端验证密码 → 返回 {access_token: "xxx"}
       → 前端存入 localStorage["chat_token"]
       → 前端调 GET /api/users/me 获取用户信息

后续请求: 前端自动在 Header 中携带
         Authorization: Bearer xxx
```

### 5.2 对话管理流程

```
登录后:    → GET /api/conversations → 加载会话列表
新建对话:  → 不发请求，仅进入草稿态（activeId=null，清空消息区）
草稿首发:  → POST /api/conversations 创建记录 → POST /api/chat 发送消息
切换对话:  → GET /api/conversations/{id}/messages → 加载历史
删除对话:  → DELETE /api/conversations/{id} → 级联删除消息
```

### 5.3 流式聊天流程（核心）

```
用户输入消息并点发送
    │
    ▼
前端: POST /api/chat {conversation_id, message}
      Header: Authorization: Bearer xxx
    │
    ▼
后端:
  1. JWT 校验 → 获取当前用户
  2. 验证对话归属（防止越权）
  3. 用户消息存入数据库
  4. 首条消息自动更新对话标题
  5. 从数据库加载完整历史
  6. 组装 LLM 上下文: [system_prompt, ...history]
  7. 调用 OpenAI SDK (stream=True)
  8. 逐 token 通过 SSE 返回前端
  9. 流结束后，完整 AI 回复存入数据库
    │
    ▼
前端: fetch 读取 ReadableStream
  - 逐块解析 SSE: data: {"content": "片段"}\n\n
  - 追加到本次请求对应的 AI 消息 → 打字机效果
  - 收到 data: [DONE]\n\n → 结束
```

## 七、关键架构决策记录

### 决策 1：数据库从同步改为异步

**背景：** fastapi-users 14 要求异步 SQLAlchemy。
**决策：** 全部使用异步（`create_async_engine` + `aiosqlite`），保持一致性。
**代价：** Alembic 不支持异步，迁移时需去掉 `+aiosqlite` 前缀转同步引擎。

### 决策 2：流式响应用独立数据库 Session

**背景：** `StreamingResponse` 的生成器在请求依赖（`Depends`）的 Session 关闭后仍在运行。
**决策：** `stream_and_save` 函数内用 `async_session_maker()` 自建独立 Session 保存 AI 回复，不依赖注入的 Session。
**收益：** 避免在已关闭的 Session 上操作数据库。

### 决策 3：LLM 调用与 SSE 格式化解耦

**背景：** 最初 `llm.py` 同时负责调用 LLM 和拼装 SSE 格式。
**决策：** `stream_chat_raw` 只返回原始文本片段，SSE 的 `data: {...}` 格式化由 chat 路由负责。
**收益：** 职责清晰，`llm.py` 可复用于非 SSE 场景。

### 决策 4：草稿式新建对话

**背景：** 用户未选中对话时直接发送消息，需要先创建对话记录再调用聊天接口。最初用 `setTimeout` 等待 `activeId` 触发下一轮 render，存在时序竞态；同时“新建对话”按钮立即落库，容易产生空会话。
**决策：** “新建对话”只清空选中状态和消息区，不创建数据库记录。首次发送时才调用创建接口；`useChat.sendMessage` 支持显式传入 `targetConversationId`，创建后立即使用新 ID 发送；同时用发送中的会话标记避免历史加载请求覆盖本地流式消息。
**收益：** 只有用户提交首条消息时才创建资源，侧边栏不会因为点击“新建”而积累空对话；发送不依赖 React 重渲染时序，也避免连续回车重复创建。
