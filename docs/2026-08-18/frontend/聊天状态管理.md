# 前端聊天状态与会话列表管理

> 本文按当前源码复核，替代早先按 `activeId` 变化推导历史请求的说明。
> 开发文档是历史记录；实际实现以源码和运行结果为准。

## 1. 目标和模块分工

当前聊天前端要满足：

1. 会话 A 正在接收 SSE 回复时，用户可以切到会话 B；
2. 切回 A 后，UI 继续读取 `chats[A].messages`，A 的流式请求不被中断；
3. 消息、输入草稿、生成状态、历史加载状态按会话隔离；
4. 新会话首次发送不请求会话历史；创建和聊天完成后仍刷新会话列表；
5. 停止、重发、删除、登出和账号切换后的旧响应不能修改新状态；
6. 会话列表不被慢列表响应或旧账号响应覆盖。

模块分工如下：

| 模块                                     | 职责                                                                     |
| ---------------------------------------- | ------------------------------------------------------------------------ |
| `frontend/src/App.tsx`                   | 连接登录状态、会话列表和聊天 UI；组织新会话首次发送的显式调用顺序        |
| `frontend/src/hooks/useConversations.ts` | 管理会话列表；校验 list/create/delete 响应是否仍能修改当前 UI            |
| `frontend/src/hooks/useChat.ts`          | 读取当前选中会话的 Zustand selector；暴露 store action；处理账号缓存重置 |
| `frontend/src/stores/chatStore.ts`       | 保存当前会话 ID、每个会话的聊天缓存、历史请求和 SSE 请求                 |
| `frontend/src/components/MessageList`    | 展示消息并控制长对话滚动                                                 |

`useConversations` 不保存当前选中会话，`useChat` 也没有同步选中值的 effect。
当前选中会话只保存在 `chatStore.activeConversationId`。

## 2. 聊天状态模型

`chatStore` 的可渲染状态是：

```typescript
interface ChatStoreState {
  chats: Record<number, ConversationChatState>;
  draftInput: string;
  activeConversationId: number | null;
}
```

每个已创建会话在 `chats[id]` 中有独立缓存：

```typescript
interface ConversationChatState {
  messages: Message[];
  isLoading: boolean;
  historyLoaded: boolean;
  historyLoading: boolean;
  historyError: string | null;
  draftInput: string;
}
```

字段含义：

| 字段             | 含义                                           |
| ---------------- | ---------------------------------------------- |
| `messages`       | 该会话当前展示的消息；来源是历史接口或本轮 SSE |
| `isLoading`      | 该会话是否正在接收 AI 回复                     |
| `historyLoaded`  | `messages` 是否已经可以直接展示                |
| `historyLoading` | 历史请求是否正在执行，用于防止重复请求         |
| `historyError`   | 历史请求失败原因；`null` 表示无错误或尚未请求  |
| `draftInput`     | 该会话自己的输入草稿                           |

`historyLoaded=true` 有三种来源：

1. `loadHistory(id)` 成功写入服务端历史；
2. `sendMessage` 在网络请求发出前插入本轮用户消息和 assistant 空消息；
3. `adoptCreatedConversation(id)` 为刚创建且必然为空的会话建立缓存。

后两种情况下，较晚返回的历史响应不能再覆盖当前本地消息。

顶层 `draftInput` 只用于尚未创建的新对话。创建并发送后，后续输入写入
`chats[id].draftInput`，不会跟随用户切换到其他会话。

## 3. 会话选择动作

`activeConversationId` 没有通用 setter，只通过明确动作修改：

| 入口                             | `activeConversationId`    | 其他行为                                      |
| -------------------------------- | ------------------------- | --------------------------------------------- |
| `startDraftConversation()`       | 设为 `null`               | 不调用创建接口，不中断请求                    |
| `selectExistingConversation(id)` | 设为 `id`                 | 调用 `loadHistory(id)`                        |
| `adoptCreatedConversation(id)`   | 设为 `id`                 | 建立空 `chats[id]`，设置 `historyLoaded=true` |
| `removeConversationChat(id)`     | 删除当前会话时设为 `null` | 中断该会话请求并删除缓存                      |
| `resetChatStore()`               | 设为 `null`               | 中断全部请求并清空账号相关缓存                |

点击侧边栏已有会话时：

```text
Sidebar onSelect(id)
  ↓
App 调用 selectExistingConversation(id)
  ↓
activeConversationId=id
  ↓
useChat 的 selector 改为读取 chats[id]
  ↓
loadHistory(id) 按缓存状态决定是否请求历史
```

点击“新对话”时：

```text
Sidebar onNew
  ↓
App 调用 startDraftConversation()
  ↓
activeConversationId=null
  ↓
输入写入顶层 draftInput
```

这一步不创建数据库记录，也不影响其他会话正在进行的 SSE。

## 4. 新会话首次发送

`App.handleSend` 有五个前置检查：

1. 创建请求正在执行，避免重复创建；
2. 当前会话正在生成，等待本轮完成；
3. 历史请求正在执行，避免历史响应和本地发送更新交错到达；
4. 历史请求失败，先重试恢复完整上下文；
5. 输入为空，后端不需要处理空消息。

当 `activeConversationId === null` 时，首次发送顺序是：

```text
1. createConversation()
   POST /api/conversations
   成功后把新记录插入本地会话列表

2. adoptCreatedConversation(newId)
   建立空 chats[newId]
   historyLoaded=true
   activeConversationId=newId
   不请求历史

3. sendMessage(newId)
   读取顶层 draftInput
   请求发出前插入用户消息和 assistant 空消息
   POST /api/chat 并读取 SSE

4. refreshConversations()
   首条消息可能触发后端更新标题
```

创建接口失败时，App 显示错误，`activeConversationId` 仍为 `null`，不会建立
`chats[newId]`，也不会发送聊天请求。

`sendMessage(newId)` 必须显式传 ID，因为新会话的输入仍在顶层 `draftInput`，
还没有迁移到 `chats[newId].draftInput`。已选中会话则必须调用 `sendMessage()`，
让 store 读取该会话自己的草稿：

| 调用                 | 发送目标                    | 草稿来源                                 |
| -------------------- | --------------------------- | ---------------------------------------- |
| `sendMessage()`      | `activeConversationId`      | `chats[activeConversationId].draftInput` |
| `sendMessage(newId)` | `newId`，仅限新会话首次发送 | 顶层 `draftInput`                        |

`adoptCreatedConversation` 会先处理同 ID 的旧流式请求：

```typescript
abortControllers.get(conversationId)?.abort();
abortControllers.delete(conversationId);
```

后端数据重置后可能复用数字会话 ID。如果旧 `id` 仍有 SSE 请求，新会话拿到
同一个 `id` 时必须先中断并移除旧 controller，否则旧响应稍后可能通过
controller 比较并把内容写入新缓存。

## 5. 历史加载

`selectExistingConversation(id)` 和历史错误重试会调用 `loadHistory(id)`。
发起请求前先读取本地缓存：

```typescript
if (chat?.isLoading || chat?.historyLoaded || chat?.historyLoading) {
  return;
}
```

三个条件分别表示：

1. 本地正在接收流式内容，不用历史覆盖；
2. 当前消息缓存已经可用；
3. 同一个历史请求已经在执行。

通过检查后，`loadHistory` 先同步设置 `historyLoading=true`，再等待
`GET /api/conversations/{id}/messages`。这样并发调用会被上述条件拦住。

响应返回时还要检查：

1. `storeGeneration` 未变化，账号未重置或切换；
2. `chats[id]` 仍存在，会话未被删除；
3. `historyLoaded` 仍为 `false`，本地没有先建立更新的消息内容。

检查通过后才把后端消息写入 `chats[id].messages`，并设置：

```text
historyLoaded=true
historyLoading=false
historyError=null
```

历史接口失败时保留：

```text
messages=已有内容
historyLoaded=false
historyLoading=false
historyError=错误信息
```

UI 显示错误 Alert，发送入口被禁用，用户点击重试后才会再次请求。这样避免
把加载失败伪装成空会话；后端生成时仍会使用数据库中的完整上下文。

## 6. 发送消息和 SSE

`sendMessage` 先确定发送目标和草稿来源：

```typescript
const currentConversationId =
  targetConversationId ?? get().activeConversationId;

const draftSourceId =
  targetConversationId === undefined ? get().activeConversationId : null;
```

空文本和生成中的会话直接返回。随后在请求发出前插入：

```text
用户消息：id 为前端临时 ID，content 为输入文本
assistant 空消息：id 为前端临时 ID，用于承接 SSE 内容
```

并同时更新：

```text
isLoading=true
historyLoaded=true
historyLoading=false
historyError=null
draftInput 清空
```

模型上下文由后端根据 `conversation_id` 从数据库读取。前端请求只携带最新
用户输入，不把本地缓存拼进请求体。

每个流式请求有自己的 `AbortController`，并记录发送开始时的
`storeGeneration`。每次异步读取返回后，修改状态前必须通过：

```typescript
const canWriteCurrentStream = () =>
  storeGeneration === requestGeneration &&
  !controller.signal.aborted &&
  abortControllers.get(currentConversationId) === controller &&
  Boolean(get().chats[currentConversationId]);
```

四个条件分别处理账号重置、用户停止、停止后立即重发、会话删除。

SSE 读取流程：

```text
reader.read()
  ↓
decoder.decode(value, { stream: true })
  ↓
buffer 按 \n\n 切分完整事件
  ↓
parseSSEChunk 解析 data
  ↓
content 追加到 assistantMsg.id 对应的消息
```

`stream: true` 保留不完整的多字节字符，避免中文在网络分块边界出现乱码。
最后一段不完整数据继续留在缓冲区。

后端约定：

```text
data: {"content": "..."}    文本片段
data: {"error": "..."}      流式错误
data: [DONE]                正常结束
```

解析到 `[DONE]` 后会同时跳出事件循环和读取循环，并调用 `reader.cancel()`
释放响应流；关闭失败可以忽略，因为后端可能已经先关闭。

非 abort 错误会写入本轮 assistant 消息：

```text
[请求失败] 错误信息
```

用户主动停止时保留已接收内容。请求收尾时只有 Map 中仍是自己的 controller，
才删除句柄并把 `isLoading` 设为 `false`，避免旧请求收尾误关新请求。

## 7. 会话列表管理

`useConversations(enabled)` 只管理 `conversations`，不管理当前选中会话。
`enabled` 通常等于 `!!user`。

登出或未登录时：

```text
guardRef.current=null
conversations=[]
```

当前选中会话和聊天缓存由 `useChat` 的账号重置逻辑处理，列表 Hook 不保存
第二份 `activeId`。

### 7.1 登录状态标识

每个异步请求会记录发起时的 `sessionToken`。响应返回后比较它和当前
`guardRef.current.sessionToken`：

| 时机             | 行为                              |
| ---------------- | --------------------------------- |
| 登录后第一次请求 | 创建新的 `sessionToken`           |
| 登出             | 将 `guardRef.current` 置为 `null` |
| 重新登录         | 创建新的 `sessionToken`           |

list 响应必须同时匹配登录状态和列表版本；create/delete 响应只要求登录状态
匹配，因为它们不是并发返回的列表请求结果。

### 7.2 列表版本标识

`listToken` 表示当前 UI 接受哪一份列表版本。以下操作会替换它：

| 操作                 | 原因                         |
| -------------------- | ---------------------------- |
| 发起新的 `refresh()` | 只接受最新 list 请求         |
| 创建会话后本地插入   | 防止慢 list 响应丢掉新会话   |
| 删除会话后本地移除   | 防止慢 list 响应加回已删会话 |
| 本地更新标题         | 防止慢 list 响应覆盖新标题   |

`refresh()` 即使返回过期结果，也把原始数组返回给调用方，只是不调用
`setConversations`。这保留了接口结果，便于外层记录或处理。

### 7.3 创建和删除

创建流程：

```text
记录请求前的 sessionToken
  ↓
POST /api/conversations
  ↓
sessionToken 仍匹配
  ↓
replaceListToken()
setConversations(prev => [conv, ...prev])
```

`create` 只修改列表，不设置当前会话。当前会话由随后的
`adoptCreatedConversation(newId)` 设置。

删除流程：

```text
记录请求前的 sessionToken
  ↓
DELETE /api/conversations/{id}
  ↓
sessionToken 仍匹配
  ↓
replaceListToken()
setConversations(prev => prev.filter(c => c.id !== id))
```

App 在删除接口完成后调用 `removeConversationChat(id)`，中断该会话请求并
删除本地聊天缓存；如果删除的是当前会话，`activeConversationId` 回到 `null`。

## 8. 账号切换与缓存重置

Zustand store 是 SPA 全局状态，不会因为登录页渲染而自动销毁。`useChat(userId)`
在用户 ID 变化或组件卸载时执行清理 effect：

```text
userId 变化或组件卸载
  ↓
storeGeneration+1
  ↓
abort 所有流式请求并清空 abortControllers
  ↓
chats={}
draftInput=""
activeConversationId=null
```

旧请求返回后发现 `storeGeneration` 已变化，不能再修改新账号状态。

账号边界有两套机制：

| 机制              | 位置                  | 作用                           |
| ----------------- | --------------------- | ------------------------------ |
| `storeGeneration` | `chatStore.ts`        | 拒绝旧账号历史响应和 SSE 内容  |
| `sessionToken`    | `useConversations.ts` | 拒绝旧账号列表、创建和删除响应 |

## 9. React selector 和渲染

`useChat(userId)` 从 store 读取：

```typescript
const activeConversationId = useChatStore(
  (state) => state.activeConversationId,
);

const input = useChatStore(selectInput(activeConversationId));
const messages = useChatStore(selectMessages(activeConversationId));
const isLoading = useChatStore(selectIsLoading(activeConversationId));
const isHistoryLoading = useChatStore(
  selectIsHistoryLoading(activeConversationId),
);
const historyError = useChatStore(selectHistoryError(activeConversationId));
```

未选中会话时，`selectMessages(null)` 返回模块级 `EMPTY_MESSAGES`，避免每次
selector 执行都生成新数组引用并触发额外渲染。

`updateChat` 更新某个会话时会复制外层 `chats` 和目标会话对象，其余会话保持
原引用。因此 A 会话追加内容时，当前展示 B 的消息 selector 仍返回同一个引用。

消息列表的滚动策略：

| 场景                      | 行为                             |
| ------------------------- | -------------------------------- |
| 新消息或切换会话          | 滚动到底部                       |
| 同一条 assistant 消息追加 | 只有用户本来在底部 80px 内才跟随 |

`MessageItem` 使用 `memo`。流式输出时通常只有当前 assistant 消息的
`content` 变化，历史消息可以跳过重渲染。

## 10. 验证清单

构建验证：

```bash
cd frontend
npm run build
```

建议手工验证：

| 场景                          | 预期                                 |
| ----------------------------- | ------------------------------------ |
| A 生成中切到 B，再切回 A      | A 内容继续增长                       |
| 新对话输入后直接发送          | 创建、聊天和列表刷新，无历史请求     |
| 点击已有未缓存会话            | 触发一次历史请求，重复点击不重复触发 |
| 历史接口失败                  | 显示错误，发送禁用，重试后恢复       |
| A 生成中停止后立即重发        | 新请求 loading 不被旧请求收尾误关    |
| 删除生成中的 A                | 请求中断，`chats[A]` 删除            |
| A 有未发送草稿时切到 B        | B 草稿为空，切回 A 后草稿恢复        |
| 后端返回 `[DONE]`             | 前端停止读取并释放响应流             |
| 登出后登录另一账号            | 不显示旧列表、旧会话或旧聊天缓存     |
| 慢 list 响应晚于创建/删除返回 | 不能覆盖本地列表                     |
| 长对话流式输出时向上滚动      | 不被新内容强行拉回底部               |

## 11. 当前限制

1. 聊天缓存随会话数量增长，尚未做冷会话淘汰；
2. 刷新页面后未完成的 SSE 不能恢复；
3. 后端流式失败时未持久化已生成的部分 assistant 内容；
4. 多个会话同时生成时，侧边栏没有后台生成中标识；
5. `chatStore` 和 `useConversations` 的并发边界适合补充单元测试。
