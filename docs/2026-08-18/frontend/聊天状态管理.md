# 前端聊天状态与会话列表管理

> 本文合并自 2026-08-17 的聊天状态改造文档和 2026-08-18 的
> `sendMessage` 异步时序修复文档，并按当前代码更新。

## 1. 目标和当前方案

本轮改造的目标是支持：

1. 会话 A 正在流式生成时切到会话 B；
2. 再切回 A 时，还能继续看到 A 的流式输出；
3. 删除、停止、登出、历史加载失败等边界操作不产生脏状态；
4. 新会话首次发送、停止后重发、删除生成中会话等异步时序不写回旧状态；
5. 会话列表不会被慢响应或旧账号数据覆盖。

当前方案是：

```text
useConversations
  └── 管理会话列表、当前选中的会话 ID、列表异步写回守卫

chatStore（Zustand）
  └── 按会话缓存消息、生成状态、历史状态和输入草稿

useChat
  └── React 适配层，把 activeId 对应的一份状态投影给 App

MessageList / MessageItem
  └── 展示消息，并在长对话流式输出时降低重渲染范围
```

核心原则是：**当前选中的会话只决定 UI 展示哪份缓存，不决定后台请求的
生命周期**。切换会话不会 abort 流式请求，删除或登出才会清理对应请求。

## 2. 为什么使用 Zustand

旧版 `useChat` 使用一份组件内部状态：

```typescript
const [messages, setMessages] = useState<Message[]>([]);
const [isLoading, setIsLoading] = useState(false);
```

这份状态只描述“当前 UI 展示的会话”。当用户从会话 A 切到 B 时，B 的历史
会替换全局 `messages`，A 正在生成的内容没有独立位置可以保留。

Zustand store 让聊天状态脱离当前渲染投影：

```typescript
interface ChatStoreState {
  chats: Record<number, ConversationChatState>;
  draftInput: string;
  activeConversationId: number | null;
}
```

每个会话都有独立缓存：

```typescript
interface ConversationChatState {
  messages: Message[];
  isLoading: boolean;
  historyLoaded: boolean;
  historyLoading: boolean;
  historyError: string | null;
  draftInput: string;
}
```

字段含义：

| 字段             | 含义                                                   |
| ---------------- | ------------------------------------------------------ |
| `messages`       | 该会话当前展示的消息缓存                               |
| `isLoading`      | 该会话是否正在接收 AI 流式回复                         |
| `historyLoaded`  | 本地缓存是否已可用；也用于防止迟到的历史快照覆盖新状态 |
| `historyLoading` | 历史请求是否正在进行，用于防止重复触发                 |
| `historyError`   | 历史加载失败原因；`null` 表示无错误或尚未尝试          |
| `draftInput`     | 该会话独立的输入框草稿                                 |

顶层 `draftInput` 只表示“新对话尚未落库”的草稿；已落库会话的草稿保存在
`chats[id].draftInput`。

## 3. Store 动作边界

| 动作                          | 职责                                              |
| ----------------------------- | ------------------------------------------------- |
| `setInput(value)`             | 根据当前 `activeConversationId` 写入对应草稿      |
| `setActiveConversationId(id)` | 只同步 UI 选中项，不中断请求                      |
| `loadHistory(id)`             | 首次进入会话时加载服务端历史                      |
| `sendMessage(targetId?)`      | 发送消息并接收 SSE；`targetId` 用于新会话首次发送 |
| `stop(targetId?)`             | 停止指定会话；缺省为当前会话                      |
| `removeConversationChat(id)`  | 后端删除成功后清理本地缓存和请求                  |
| `resetChatStore()`            | 登出或账号变化时中断所有请求并清空缓存            |

`activeConversationId` 只影响默认发送目标和当前 UI 投影。它不承载请求生命
周期，因此切换这个值不会触发 abort。

`sendMessage` 的调用约定必须严格区分：

| 调用方式             | 草稿来源                                 | 发送目标     |
| -------------------- | ---------------------------------------- | ------------ |
| `sendMessage()`      | `chats[activeConversationId].draftInput` | 当前选中会话 |
| `sendMessage(newId)` | 顶层 `draftInput`                        | 新创建的会话 |

显式传入 ID 只表示“新对话首次发送”，不能用于普通已选中会话。否则 App 会让
store 误读顶层草稿，而不是该会话自己的草稿。

## 4. 切换会话与流式写入

选中会话 B 的流程：

```text
用户点击会话 B
  ↓
useChat(activeId=B) 同步 chatStore.activeConversationId=B
  ↓
UI 读取 chats[B]
  ↓
如果 B 需要历史且未加载，请求历史
```

历史加载的去重条件：

```typescript
if (chat?.isLoading || chat?.historyLoaded || chat?.historyLoading) {
  return;
}
```

三个条件分别表示：

1. 本地流式内容比服务端快照更新；
2. 缓存已经可用；
3. 同一个历史请求已在途中。

发送消息时会先插入 user 消息和 assistant 占位消息。每个 SSE chunk 写回前
先验证请求仍有效，再通过两个定位写入：

```text
conversationId：写入哪个会话
assistantMsg.id：写入该会话中的哪条 assistant 消息
```

因此会话 A 生成中时，即使 UI 正在展示 B，A 的 chunk 仍写入 `chats[A]`。

完整时序：

```text
1. A 生成中，chats[A].isLoading=true
2. 用户切到 B，UI 展示 chats[B].messages
3. A 的 fetch 继续执行，chunk 继续写入 chats[A].messages
4. 用户切回 A，UI 重新读取 chats[A].messages
5. 新 chunk 到达，界面继续增长
6. A 完成，chats[A].isLoading=false
```

## 5. 新会话首次发送

新建对话按钮只执行：

```text
activeId = null
```

它不会创建数据库记录，也不会中断其他会话的生成。用户第一次发送时才落库：

```text
1. App 读取顶层 draftInput
2. App 调用 conversationApi.create()
3. create 返回新会话 id
4. App 显式调用 sendMessage(newId)
5. sendMessage 从顶层草稿取输入，但写入 chats[newId]
6. 请求结束后刷新会话列表
```

这里显式传 `newId` 是为了避免依赖 React `setState` 的下一轮渲染。创建后
`activeId` 虽已更新，但 `useChat` 可能还没有收到新值；直接传目标 ID 可以
保证消息立即写入正确会话。

这里曾出现过草稿来源错误。旧逻辑把 `targetId` 同时当作发送目标和草稿来源：

```typescript
const draftSourceId = targetId ?? get().activeConversationId;
```

新会话刚创建时 `chats[newId].draftInput` 还是空字符串，导致首条消息被
`!text` 拦截。当前实现区分这两个概念：

```typescript
const draftSourceId =
  targetConversationId === undefined ? get().activeConversationId : null;
```

`draftSourceId === null` 表示读取顶层新对话草稿；否则读取当前会话草稿。
App 侧也必须遵守同一约定：

```typescript
if (isNewConversation) {
  await sendMessage(newConversationId);
} else {
  await sendMessage();
}
```

草稿来源和发送目标的关系：

| 场景           | 草稿来源                     | 发送目标        |
| -------------- | ---------------------------- | --------------- |
| 草稿态首次发送 | 顶层 `draftInput`            | 新创建的会话 ID |
| 已选中会话发送 | `chats[activeId].draftInput` | 当前 `activeId` |

## 6. 停止、重发和删除

`AbortController` 保存在模块级 Map，而不是 Zustand state：

```typescript
const abortControllers = new Map<number, AbortController>();
```

原因是 controller 是命令型句柄，不是需要渲染的数据；按会话 ID 存储也可以
精确停止某一个会话。

### 6.1 旧请求写回守卫

停止、重发、删除和账号切换都可能让一个已经发出的请求变成“旧请求”。当前
实现把流式写回条件收敛为 `canWriteCurrentStream()`：

```typescript
const canWriteCurrentStream = () =>
  storeGeneration === requestGeneration &&
  !controller.signal.aborted &&
  abortControllers.get(currentConversationId) === controller &&
  Boolean(get().chats[currentConversationId]);
```

| 条件                        | 防护场景                               |
| --------------------------- | -------------------------------------- |
| 账号代数未变化              | 登出、切换账号后的旧账号响应           |
| controller 未 abort         | 用户主动停止、删除会话                 |
| Map 中仍是自己的 controller | 停止后立即重发，新请求已替换句柄       |
| `chats[id]` 仍存在          | 会话已删除，不能通过 `updateChat` 复活 |

SSE chunk 写入和 `catch` 错误写入都使用同一套校验。这里不能只依赖
`finally`，因为错误写回发生得更早；旧请求的异常可能晚于新请求启动，如果
直接按 `assistantMsg.id` 更新，就会污染新一轮气泡。

停止后立刻重发时，可能出现：

```text
请求 A 被用户停止
  ↓
用户立刻发送请求 B
  ↓
请求 A 的 finally 晚于请求 B 启动
```

因此请求收尾时会检查 Map 中是否仍是自己的 controller。只有当前请求才允许
删除停止句柄和清理 `isLoading`，避免 A 的收尾逻辑误关 B。

删除生成中的会话时，App 先请求后端删除：

```text
DELETE /conversations/{id} 成功
  ↓
abort 该会话请求
  ↓
删除 AbortController
  ↓
删除 chats[id]
  ↓
如果删除的是当前会话，activeConversationId 置空
```

先请求后端是为了避免删除失败时本地界面提前丢失会话和已生成内容。

删除会话时，历史请求也可能仍在途中。历史响应返回后必须同时确认：

1. 账号代数没有变化；
2. `chats[id]` 仍存在；
3. 本地没有通过乐观发送建立更新的 `historyLoaded=true` 视图。

否则晚到的历史快照或历史错误可能把已删除会话重建到本地缓存。

### 6.2 SSE `[DONE]` 与流释放

网络读取 chunk 和 SSE 事件边界没有一一对应关系，因此 `sendMessage` 使用
缓冲区按空行切出完整事件：

```text
reader.read()
  ↓
decoder.decode(value, { stream: true })
  ↓
buffer 按 \n\n 切分
  ↓
最后一段不完整数据留在 buffer
  ↓
完整事件交给 parseSSEChunk
```

`stream: true` 会保留不完整的多字节字符，避免中文内容在网络分块边界上出现
乱码。

解析到 `[DONE]` 时，只跳出处理事件的 `for` 循环还不够；外层
`while (true)` 仍可能继续 `reader.read()`。当前实现会：

```text
设置 receivedDone=true
  ↓
跳出 for
  ↓
跳出 while
  ↓
reader.cancel() 释放响应流
```

`reader.cancel()` 的失败会被忽略，因为后端可能已经先关闭流。

## 7. 历史加载失败

历史加载失败后的状态是：

```text
messages 保留已缓存内容，不伪装成空数组
historyLoading=false
historyLoaded=false
historyError=错误信息
```

UI 显示错误 Alert，并提供重试按钮。发送按钮在历史失败时禁用，因为用户看
到的上下文可能不完整，但后端仍会按数据库里的完整上下文生成。

选择显式重试而不是自动重试，是为了避免网络故障时连续请求，用户却不知道
输入区为什么一直不可用。

新会话首次发送和历史加载可能并发：

```text
历史请求先发出
  ↓
sendMessage(newId) 先乐观插入消息，并设置 historyLoaded=true
  ↓
历史接口返回
  ↓
发现本地已有更新状态，丢弃旧快照
```

这样可以保证首条消息不被瞬时加载状态拦住，也不会被稍后返回的空历史覆盖。

## 8. 会话列表守卫与完整流程

`useConversations` 管理列表、`activeId` 和列表请求的写回安全。

异步请求不能只依赖 React state 判断自己是否仍有效。请求发出时的函数闭包
会固定住当时的渲染值；响应返回时，用户可能已经登出、切换账号、发起新的
列表请求，或者删除了某个会话。

因此 Hook 使用一个不参与渲染的 `guardRef` 保存当前有效守卫：

```typescript
interface ConversationRequestGuard {
  sessionToken: SessionToken;
  listToken: ListToken;
}
```

这里的 token 是 opaque token（不可解释令牌）：

1. 只比较是否相等；
2. 不比较大小；
3. 不解析内容；
4. 不当成业务 ID、认证凭证或安全随机数使用。

它的作用只有一个：让旧响应在写回前证明“我仍属于当前状态”。

### sessionToken：登录周期

| 时机                 | 行为                                  |
| -------------------- | ------------------------------------- |
| 登录后第一次需要请求 | 创建新的 `sessionToken`               |
| 登出                 | 将整个 `guardRef.current` 置为 `null` |
| 重新登录             | 再创建新的 `sessionToken`             |

账号切换时的保护流程：

```text
账号 A 发起 list 请求，请求携带 sessionToken-A
  ↓
用户登出，guardRef.current=null，列表和高亮清空
  ↓
账号 B 登录，创建 sessionToken-B
  ↓
账号 A 的旧请求返回
  ↓
sessionToken 不相等，拒绝写入
```

创建和删除接口同样在请求前记录 `sessionToken`。响应返回后先调用
`isSameSession`：

```typescript
isSameSession(guardRef.current, requestSessionToken);
```

只有仍相等，才允许修改本地列表或 `activeId`。即使后端创建/删除已经成功，
只要它属于旧登录周期，也不能影响新账号界面。

### listToken：列表快照

`listToken` 表示“当前界面接受哪一份列表快照”。以下操作都会替换它：

| 时机                 | 原因                             |
| -------------------- | -------------------------------- |
| 发起新的 `refresh()` | 只允许最新列表请求写回           |
| 创建会话后本地插入   | 在途旧列表不能把新会话挤掉       |
| 删除会话后本地移除   | 在途旧列表不能把已删会话加回来   |
| 本地更新标题         | 在途旧列表不能用旧标题覆盖新标题 |
| 登出后重新登录       | 新账号必须从新的列表状态开始     |

本地写回前的替换动作封装为 `replaceListToken()`。这个命名描述的是动作本身：
替换 token；替换后，所有携带旧 `listToken` 的在途列表响应都会失败写回校验。

它解决的是“服务端快照过期”问题：

```text
list 请求 A 发起，携带 listToken-1
  ↓
用户创建 / 删除 / 改标题，当前 listToken 变成 listToken-2
  ↓
请求 A 返回
  ↓
listToken-1 != listToken-2
  ↓
丢弃请求 A 的快照
```

典型竞态：

```text
慢 list 响应后返回
  ↓
不能覆盖更快的 list 响应

list 请求在途中用户创建会话
  ↓
旧 list 响应不能把新会话挤掉

list 请求在途中用户删除会话
  ↓
旧 list 响应不能把已删会话加回来

list 请求在途中用户修改标题
  ↓
旧 list 响应不能用旧标题覆盖新标题
```

列表响应提交前必须同时满足：

```typescript
isSameSession(guardRef.current, snapshot.sessionToken) &&
  guardRef.current.listToken === snapshot.listToken;
```

第一个条件防止跨账号写入；第二个条件防止过期列表快照覆盖更新的 UI 状态。

这只拦截“写入 React state”，不会篡改接口返回值。调用方仍能拿到原始响应，
便于日志或外层逻辑继续处理。

登出时会同时清空：

1. `conversations`
2. `activeId`
3. `guardRef.current`

否则重新登录另一个账号时，可能残留旧账号的高亮 ID 或让旧账号的慢响应写
入新账号列表。

### 核心状态与读取方式

`useConversations` 内部有两类状态：

```text
React state
  conversations  会话列表
  activeId       当前选中的会话 ID

guardRef.current
  sessionToken   当前登录周期 token
  listToken      当前接受的列表快照 token
```

React state 参与 UI 渲染；guard 不参与渲染，只在异步响应返回时做写回校验。
`guardRef.current === null` 表示当前已登出，旧账号的所有在途响应都不能写回。

请求发起时会记录当时的 token 快照；响应返回后再读取最新的 `guardRef`。
如果两个时刻的 token 不一致，说明请求期间发生了登录周期变化或列表状态
变化，响应不能再写入当前 UI。

### 登录与列表加载

登录入口：

```text
useConversations(!!user)
```

完整流程：

```text
enabled 从 false 变为 true
  ↓
useEffect 调用 refresh()
  ↓
refresh() 调用 ensureGuard()
  ↓
guardRef.current 为 null，创建新的 sessionToken / listToken
  ↓
记录本次请求的 sessionToken / listToken 快照
  ↓
GET /conversations
  ↓
响应返回后执行 canCommitList
  ↓
校验通过，setConversations(list)
```

`refresh()` 的关键顺序：

```text
1. ensureGuard() 得到或创建当前 guard
2. 记录 snapshot.sessionToken / snapshot.listToken
3. 替换 guardRef.current.listToken
4. 发起列表请求
5. 响应返回后比较 snapshot 与当前 guard
```

每次新的 `refresh()` 都会替换 `listToken`。因此更早发出的慢列表请求即使
晚于新请求返回，也不能覆盖新请求的结果。

### 登出

登出流程：

```text
enabled 从 true 变为 false
  ↓
guardRef.current = null
  ↓
conversations = []
activeId = null
```

不同在途请求返回后的结果：

| 在途请求 | 校验结果             | UI 行为                          |
| -------- | -------------------- | -------------------------------- |
| list     | `canCommitList` 失败 | 不写回列表                       |
| create   | `isSameSession` 失败 | 抛出“登录状态已变化，请重新登录” |
| delete   | `isSameSession` 失败 | 不修改列表和高亮                 |

守卫不会取消网络请求，也不会撤销后端已经完成的操作。它只保证旧账号的
响应不能污染登出后的界面或新账号的界面。

### 新建会话

点击“新建对话”属于 App 层动作，只进入草稿态：

```text
activeId = null
```

这一步不创建数据库记录，也不影响其他会话正在进行的流式生成。

用户首次发送消息时，App 才调用 `useConversations().create()`：

```text
记录请求前的 sessionToken
  ↓
POST /conversations
  ↓
响应返回
```

如果仍在同一个登录周期：

```text
isSameSession = true
  ↓
replaceListToken()
  ↓
setConversations(prev => [conv, ...prev])
setActiveId(conv.id)
```

必须先替换 `listToken`，再写入本地列表。否则一个更早发出的列表请求稍后
返回时，可能把刚创建的会话挤掉。

如果请求期间登出或切换账号：

```text
isSameSession = false
  ↓
抛出 Error("登录状态已变化，请重新登录")
```

即使后端已经创建成功，这个新会话也不能插入新账号列表，也不能成为新账号
的 `activeId`。

### 删除会话

删除流程：

```text
App 调用 useConversations().remove(id)
  ↓
记录请求前的 sessionToken
  ↓
DELETE /conversations/{id}
  ↓
响应返回
```

如果仍在同一个登录周期：

```text
isSameSession = true
  ↓
replaceListToken()
  ↓
setConversations(prev => prev.filter(c => c.id !== id))
setActiveId(prev => prev === id ? null : prev)
```

如果删除的是当前选中会话，`activeId` 会被清空。先替换 `listToken` 是为了
防止更早发出的列表响应稍后返回，把已删除的会话重新加回来。

如果请求期间登录周期变化：

```text
isSameSession = false
  ↓
直接 return
```

删除可能在后端已经成功，但旧账号的删除结果不能影响新账号界面。

### 本地更新标题

`updateTitle` 不请求后端，但它同样会改变列表状态：

```text
replaceListToken()
  ↓
setConversations(prev => 更新目标会话标题)
```

原因是更早发出的列表请求可能仍在途中。如果不替换 `listToken`，旧列表响应
返回后可能用服务端旧标题覆盖本地刚更新的标题。

### 守卫触发状态总表

| 触发点               | `sessionToken` | `listToken`  | 目的                       |
| -------------------- | -------------- | ------------ | -------------------------- |
| 登录后第一次请求     | 创建新 token   | 创建新 token | 建立新的登录周期和列表状态 |
| 发起新的 `refresh()` | 不变           | 替换         | 让更早的慢列表请求失效     |
| 创建会话成功         | 不变           | 替换         | 防止旧列表响应挤掉新会话   |
| 删除会话成功         | 不变           | 替换         | 防止旧列表响应复活已删会话 |
| 本地更新标题         | 不变           | 替换         | 防止旧列表响应覆盖新标题   |
| 登出                 | guard 置空     | guard 置空   | 旧账号所有响应都不能写入   |
| 重新登录             | 创建新 token   | 创建新 token | 新账号不能接受旧账号响应   |

### 校验规则速查

list 响应必须同时满足：

```text
1. sessionToken 匹配
2. listToken 匹配
```

对应：

```typescript
canCommitList(guardRef.current, snapshot);
```

create / delete 响应只要求：

```text
sessionToken 匹配
```

对应：

```typescript
isSameSession(guardRef.current, requestSessionToken);
```

校验通过后，如果该操作会改变列表，必须先调用 `replaceListToken()`，再
执行 `setConversations`。

## 9. 账号切换与聊天缓存

Zustand store 是 SPA 全局状态，不会随登录页面切换自动销毁。因此
`useChat(activeId, userId)` 在用户 ID 变化或组件卸载时调用
`resetChatStore()`：

```text
登出 / 切换账号
  ↓
storeGeneration + 1
  ↓
abort 所有流式请求
  ↓
清空 chats、draftInput、activeConversationId
  ↓
旧响应返回后检查 generation，不一致则拒绝写入
```

这与会话列表中的 `sessionToken` 解决同一类问题，但作用范围不同：

| 边界              | 位置                  | 作用                                               |
| ----------------- | --------------------- | -------------------------------------------------- |
| `storeGeneration` | `chatStore.ts`        | 防止旧账号的聊天历史和 SSE 写入新账号缓存          |
| `sessionToken`    | `useConversations.ts` | 防止旧账号的会话列表、创建和删除结果写入新账号列表 |

## 10. React 适配层

`useChat` 刻意保持薄：

```typescript
const input = useChatStore(selectInput(conversationId));
const messages = useChatStore(selectMessages(conversationId));
const isLoading = useChatStore(selectIsLoading(conversationId));
const isHistoryLoading = useChatStore(selectIsHistoryLoading(conversationId));
const historyError = useChatStore(selectHistoryError(conversationId));
```

它不保存聊天业务状态，也不直接调用聊天接口，只负责：

1. 订阅当前会话的 selector；
2. 同步 `activeConversationId`；
3. 首次选中会话时触发历史加载；
4. 用户变化或卸载时重置 store；
5. 向 App 暴露稳定、语义清晰的动作。

未选中会话时，`selectMessages(null)` 返回模块级稳定空数组，避免 selector
每次返回新引用导致额外渲染。

## 11. 长对话渲染

消息列表拆分为：

```text
MessageList
  ├── 滚动容器和滚动策略
  └── MessageItem（memo）
        ├── 头像与布局
        └── Markdown / 用户文本 / typing indicator
```

流式更新时，只有当前 assistant 消息的 `content` 变化；历史消息 props 保持
稳定，因此可以跳过重渲染。

自动滚动区分两类场景：

| 场景               | 行为                           |
| ------------------ | ------------------------------ |
| 新消息或切换会话   | 滚动到底部                     |
| 同一条消息流式追加 | 只有用户本来就在底部附近才跟随 |

这样用户回看上文时，不会被每个 SSE chunk 强行拉回底部。

## 12. 验证清单

构建验证：

```bash
npm run build
```

建议手工验证：

| 场景                        | 预期                                      |
| --------------------------- | ----------------------------------------- |
| A 生成中切到 B，再切回 A    | A 的流式内容继续增长                      |
| A 生成中停止后立刻重发      | 新请求的 loading 不被旧请求收尾误关       |
| 删除生成中的 A              | 请求中断，`chats[A]` 清理，不显示幽灵会话 |
| 删除历史请求仍在途的 A      | 迟到历史不能重建本地会话                  |
| 新对话输入后直接发送        | 首条消息进入新会话，不从空会话草稿读取    |
| 后端返回 `[DONE]`           | 前端停止读取并释放响应流                  |
| A 输入未发送，切到 B        | B 输入框为空；切回 A 后草稿恢复           |
| 历史接口失败                | 显示错误，发送禁用；重试成功后恢复        |
| 登出后登录另一账号          | 不显示旧列表、旧高亮或旧聊天缓存          |
| 列表请求慢时创建 / 删除会话 | 旧列表响应不能覆盖本地结果                |
| 长对话流式输出时向上滚动    | 不被新 chunk 自动拉回底部                 |

## 13. 当前限制和后续方向

1. 前端聊天缓存会随会话数量增长，后续可按 LRU 淘汰冷会话；
2. 刷新页面后未完成的流式过程不能恢复，需要服务端任务化和可恢复事件流；
3. 后端流式出错时不会持久化已生成的部分 assistant 内容；当前前端只在本地
   气泡保留已接收内容和错误提示，缓存重建后以数据库为准；
4. 多会话同时生成时，侧边栏还没有后台生成中标识；
5. `chatStore` 和 `useConversations` 的并发场景适合补充 Vitest 单元测试。
